Telegram-бот и публичный сайт сервиса подписок на Go. Это переписывание
Python-версии (`../vivid-bot`) с сохранением схемы базы: существующая
установка поднимается на том же Postgres, а старые заказы и подписки
остаются на месте.

Один процесс делает всё: принимает обновления Telegram, отдаёт сайт и
вебхуки платёжных шлюзов, доводит фоновые задачи. Отдельного воркера и
брокера нет.

Обрыв связи с Telegram не роняет сервис: сайт, вебхуки и фоновые задачи
продолжают работать, бот переподключается сам.

## Стек

| Задача | Решение |
| --- | --- |
| Telegram | [`telego`](https://github.com/mymmrac/telego) + `telegohandler`, long polling |
| База | PostgreSQL, `pgx/v5` + `pgxpool`; запросы — руками, `sqlc.yaml` — заготовка |
| Сайт | стандартный `html/template`, встроенный через `go:embed` |
| Оформление | CSS-переменные + `theme.json`, переопределение шаблонов из `WEB_DIR` |
| Деньги | `int64` в копейках (`domain.Money`), в базе — `NUMERIC(12,2)` |
| Фоновые задачи | горутины под `errgroup`, остановка по `SIGINT`/`SIGTERM` |

## Быстрый старт

```bash
cp .env.example .env     # заполнить BOT_TOKEN, API_BASE_URL, API_TOKEN, ADMIN_IDS
docker compose up --build -d
```

Для существующей базы можно задать `DOCKER_DATABASE_URL` в `.env`:
из контейнера адрес базы на компьютере — `host.docker.internal`, а не
`localhost`. `DOCKER_WEB_PORT` задаёт внешний порт сайта (по умолчанию 8080).
Внутри контейнера приложение слушает `0.0.0.0:8080`.

Сайт и вебхуки слушают `:8080`:

```bash
curl http://localhost:8080/healthz
```

Локально без Docker (нужен свой Postgres):

```bash
go run ./cmd/vivid
```

Настройки читаются из `.env` рядом с программой, но уже заданные
переменные окружения не перезаписываются. Сайт поднимается на том адресе,
что в `WEBHOOK_HOST:WEBHOOK_PORT` (по умолчанию `127.0.0.1:8081`):

```bash
curl http://127.0.0.1:8081/healthz
```

Схема применяется при старте: DDL идемпотентен, отдельный шаг миграций не
нужен. Стартовый каталог тарифов (`30d`, `90d`, `180d`) и пакетов устройств
(`dev1`, `dev3`, `dev5`) наполняется только на пустых таблицах — дальше
цены живут в базе.

### Переход с Python-версии

Схема совместима, поэтому база переезжает как есть. Два шага выполняются
автоматически при первом старте:

- DDL добавляет недостающие колонки (`accounts.source`, `accounts.ref_code`,
  `accounts.merged_into`, `promocodes.partner_id`) — `CREATE TABLE IF NOT
  EXISTS` на существующей таблице ничего не добавляет, поэтому для них
  есть отдельные `ALTER TABLE`.
- Перенос `subject_id` (`storage.MigrateSubjects`): субъект заводится всем,
  кто известен базе, а в таблицах (`trials`, `user_balance`,
  `user_referral_mode`, `promo_activations`, `pending_referral_bonuses`,
  `withdrawal_requests`, `referrals`) проставляется ссылка на субъекта.
  Без этого человек получил бы второй пробный период и пустой баланс.
  Шаг идемпотентен и под advisory-блокировкой: выполняет его ровно одна
  копия приложения.


## Обязательные настройки

| Переменная | Зачем |
| --- | --- |
| `BOT_TOKEN` | токен бота от @BotFather |
| `DATABASE_URL` | строка подключения к Postgres |
| `API_BASE_URL`, `API_TOKEN` | панель Remnawave: выдача и продление подписок |
| `ADMIN_IDS` | Telegram ID сотрудников через запятую; первый — владелец |

Всё остальное — в `.env.example` с комментариями. Часть настроек (бренд,
цены, сроки, тексты) можно переопределить в таблице `app_settings`: они
накладываются поверх окружения и читаются при старте.

## Что где

```
cmd/vivid/main.go        сборка процесса, старт и остановка
cmd/dbcheck              проверка миграций и переноса субъектов на живой базе
cmd/websmoke             подъём сайта против базы и обход страниц
internal/config          настройки: окружение + app_settings
internal/domain          деньги, тарифы, заказы, подписки — без I/O
internal/storage         пул, миграции, репозитории и журнал выдачи (единственный SQL)
internal/remnawave       клиент панели
internal/payments        шлюзы, заказы, выдача, устройства, доступ
internal/bot             экраны и диалоги Telegram
internal/mdhtml          Markdown → HTML для Telegram и сайта, rich-разметка
internal/botui/legacy    рендерер и клиент богатых сообщений Bot API (sendRichMessage)
internal/web             сайт, кабинет, админка, поддержка, вебхуки
internal/support         помощник поддержки на базе LLM
internal/llm            клиент говорящей модели
internal/jobs            выдача оплаченного, напоминания, лимит устройств
internal/web/templates   встроенные шаблоны страниц
internal/web/static      встроенные стили и иконка
```

Логика денег и доступа живёт только в `internal/payments`. Бот и сайт
вызывают его и раскладывают результат по кнопкам и страницам.

## Сайт

| Адрес | Назначение |
| --- | --- |
| `/` | витрина: тарифы, преимущества, FAQ |
| `/buy` | оформление подписки (POST требует входа) |
| `/login`, `/auth/google`, `/auth/google/callback` | вход по коду из бота или через Google |
| `/account` | кабинет: подписка, заказы, устройства, промокод |
| `/connect` | инструкции и клиенты |
| `/support`, `/support/tickets/{id}` | поддержка; для гостя — форма без входа |
| `/support/tickets/{id}/updates` | живая переписка (SSE): ответ приходит без перезагрузки |
| `/partner`, `/partner/claim?token=...` | кабинет партнёра и привязка аккаунта по приглашению |
| `/admin` | админка: сводка, промокоды, партнёры, обращения, журнал |
| `/terms`, `/privacy` | документы |
| `/happ?u=...` | мостик `happ://add/...` для кнопки «Подключить в Happ» |
| `/healthz` | проверка живости |
| `POST /webhooks/{provider}` | вебхуки `wata`, `platega`, `yookassa` |

Вход без Google: в боте `/weblogin` выдаёт одноразовый код, его можно
ввести на `/login` (или открыть ссылку из сообщения). Привязка Telegram к
веб-аккаунту — через `t.me/<bot>?start=link_<код>`.

Сессии лежат в базе (хранится `sha256` токена), cookie — `HttpOnly`,
`SameSite=Lax`, `Secure` при https (учитывается `X-Forwarded-Proto`).
Формы защищены double-submit CSRF и грубым рейт-лимитом.

### Админка

Отдельная панель на сайте, вход тот же — через Google. Доступ только у
сотрудников: чей Telegram в `ADMIN_IDS` (владелец) или в таблице `staff`.
Обычный зарегистрировавшийся человек получает 403, а не пустую страницу.

| Адрес | Что делает |
| --- | --- |
| `/admin` | сводка: клиенты, выручка, воронка, последние заказы, заявки с сайта |
| `/admin/promos` | промокоды: создание, включение, привязка партнёра и его награды |
| `/admin/partners` | партнёры программы |
| `/admin/partners/{id}` | карточка партнёра: контакты, коды, начисления, приглашение |
| `/admin/tickets` | очередь обращений |
| `/admin/audit` | журнал действий сотрудников |

### Партнёрская программа

Партнёр получает ссылку-приглашение, открывает её и входит тем же
Google-аккаунтом — аккаунт привязывается к партнёрству, и начисления с
этого момента идут на его внутренний баланс. Промокод партнёра может
нести награду: процент с тарифа или фиксированную сумму, по всем
покупкам клиента или только по первой. Начисление привязано к заказу,
поэтому повторный вебхук не задваивает его.

### Помощник поддержки

Модель отвечает на типовые вопросы сам («сколько стоит», «как
подключить», «почему не пришла подписка»). Просьба живого человека, любые
персональные данные и вопросы не о сервисе уходят сотруднику сразу —
такие сообщения модель вообще не видит.

Говорящий API один: OpenAI-совместимый `/v1/chat/completions`. Подойдут
и OpenAI, и Ollama (`http://127.0.0.1:11434`), и всё, что притворяется ими.

```
SUPPORT_LLM_ENABLED=true
SUPPORT_LLM_URL=http://127.0.0.1:11434
SUPPORT_LLM_MODEL=qwen2.5:7b
SUPPORT_LLM_SHARE=80      # доля обращений, на которые отвечает помощник
```

Ответ помощника приходит и на страницу обращения, и в Telegram.
Отвечает он по базе знаний `WEB_DIR/knowledge.md` и по фактам о сервисе,
которые есть в программе: тарифы, пробный период, способы оплаты, лимит
устройств, состояние подписки и баланс конкретного человека.

### Разметка в сообщениях

Ответы помощника и сотрудников поддержки считаются Markdown — так модель
их и пишет, а человеку не нужно помнить про HTML. Разметка переводится в
тот HTML, который понимает Telegram: жирный, курсив, зачёркнутый, спойлер,
код, ссылки, заголовки, цитаты, списки и таблицы.

В Telegram бот отправляет их **богатыми сообщениями** (`sendRichMessage`):
заголовки, настоящие таблицы, списки с чекбоксами, цитаты, сноски и кнопки
внутри текста выглядят как в документе, а не как строка с тегами. Экраны
«Главное меню», «Моя подписка», «Выбор тарифа» и «Устройства» тоже собираются
богатыми. Обычные inline-кнопки автоматически превращаются в
`<tg-button-row>`; если хоть одну кнопку нельзя выразить rich-тегом,
клавиатура остаётся обычной, чтобы действие не пропало.

Если сервер не знает `sendRichMessage` (старый Bot API или локальный
сервер), бот один раз это замечает и дальше работает на обычном HTML.
Если Telegram не принял конкретное сообщение, оно повторяется простым
текстом, а длинный Markdown делится на части по границам блоков — код и
списки не разрезаются посередине.

В Markdown можно вставлять кнопки:

```markdown
[Купить](btn:nav:buy)
[Сайт](btn-url:https://example.com)
```

Строка, состоящая только из таких кнопок, становится отдельным рядом.

Выключить богатые сообщения можно через `RICH_MESSAGES_ENABLED=false`.

Всё, что не разобрано как разметка, экранируется: `<script>` остаётся
текстом, а непарная звёздочка не срывает доставку. Ссылки пропускаются
только с `http`, `https`, `tg` и `mailto`.

На сайте та же разметка показывается в переписке обращения и в живых
обновлениях. Рендерер — `internal/mdhtml`, настраивать там нечего; стили
сообщений задаются в `WEB_DIR/static/style.css` (`.message-text`).

### Переезд на другой сервис

Другой проект может взять этот код и переписать под себя и сайт, и бота,
не трогая Go:

| Что | Где настраивается |
| --- | --- |
| Цвета, шрифт и тексты витрины | `WEB_DIR/theme.json` |
| **Конструктор витрины**: блоки страницы и их порядок | `WEB_DIR/theme.json` → `blocks` |
| Отдельная страница сайта целиком | `WEB_DIR/templates/*.html` |
| Стили | `WEB_DIR/static/style.css` |
| Тексты бота и подписи кнопок | `WEB_DIR/bot.json` |
| Подписи rich-экранов: колонки таблиц, сноски, подсказки | `WEB_DIR/bot.json` → `rich` |
| **Конструктор меню бота**: кнопки, порядок, видимость | `WEB_DIR/bot.json` → `menu` |
| Характер бота: маскот, приветствия по времени суток | `WEB_DIR/bot.json` → `persona` |
| База знаний для помощника | `WEB_DIR/knowledge.md` |
| Бренд, контакты, юридические ссылки, часовой пояс | `BRAND_NAME`, `SUPPORT_EMAIL`, `TERMS_URL`, `TIMEZONE`… |
| Каталог тарифов и пакетов | таблицы `plans` и `device_packs` |

Тексты в `bot.json` и `theme.json` перекрывают встроенные: заданные ключи
заменяются, остальные остаются.

**Конструктор витрины.** Страница собирается из блоков в порядке, который
задан в `theme.json`:

```json
{ "blocks": [
  { "type": "hero", "title": "...", "links": [{"label": "Купить", "href": "/buy"}] },
  { "type": "features", "items": [{"icon": "⚡", "title": "...", "text": "..."}] },
  { "type": "plans" },
  { "type": "steps", "steps": ["Первый шаг", "Второй шаг"] },
  { "type": "faq", "items": [{"q": "...", "a": "..."}] },
  { "type": "cta", "links": [{"label": "Купить", "href": "/buy"}] }
] }
```

Виды блоков: `hero`, `features`, `plans`, `faq`, `steps`, `text`, `cta`.
Блоков нет — берутся встроенные.

**Конструктор меню бота.** Раскладка задана по состояниям подписки
(`active`, `inactive`, `unknown`), у кнопки — свои условия показа:

```json
{ "menu": {
  "layout": { "active": [["subscription"], ["renew", "devices"]] },
  "buttons": {
    "trial": {"label": "🎁 Попробовать", "action": "nav:trial", "require": ["trial"]},
    "channel": {"label": "📣 Канал", "url": "https://t.me/example", "when": ["active"]}
  }
} }
```

`require` — условия показа (`payments`, `trial`, `devices`): кнопка исчезает
сама, когда условие не выполнено. `when` — состояния, в которых кнопка
нужна. Ряд можно упаковать по две кнопки: `{"pack": 2, "buttons": [...]}`.
Кнопка с `url` ведёт наружу, с `action` — вызывает действие бота.

## Оформление и шаблоны

По умолчанию всё встроено в бинарник. Каталог `WEB_DIR` (по умолчанию
`web`) может частично переопределить вёрстку и тексты:

```
web/
  theme.json            # цвета и тексты витрины
  bot.json              # тексты бота (необязательно)
  knowledge.md          # база знаний для помощника (необязательно)
  templates/*.html      # заменить отдельную страницу
  static/*              # заменить style.css или favicon.svg
```

- `theme.json` мержится поверх встроенной темы: достаточно указать только
  изменившиеся поля. Ключи — как в `web/theme.example.json`.
- Цвета превращаются в CSS-переменные `:root`: `"accent": "#6d5efc"` →
  `--accent: #6d5efc`.
- `bot.json` — то же для бота: заданы только те ключи, которые нужно
  переписать, остальные остаются встроенными. Пример — `web/bot.example.json`.
  Ключи устроены по экранам (`main.title`, `buttons.menu`, `support.lead`),
  в текстах работают подстановки `{{.Brand}}`, `{{.Currency}}` и другие.
  Ошибка разбора файла — отказ запуска: молча половина текстов на старом
  языке хуже явной остановки.
- `knowledge.md` (и дополнительные `knowledge-*.md`) — то, о чём помощник
  поддержки рассказывает сам: как подключиться, что делать с оплатой, когда
  возвращают деньги. Персональные данные клиента сюда не кладутся: они
  подставляются отдельно. Пример — `web/knowledge.example.md`.
- Шаблоны читаются по одному: можно заменить `landing.html`, не копируя
  остальные.
- Значения из окружения (`BRAND_NAME`, `SUPPORT_EMAIL`, `TERMS_URL` и т. п.)
  главнее файла темы: это факты о сервисе, а не оформление.
- Темплейты компилируются на старте: ошибка в файле — отказ запуска, а не
  кривая страница у человека.

Список страниц: `landing`, `buy`, `login`, `account`, `connect`, `support`,
`ticket`, `documents`, `pay_result`, `notice`. Каждая собирается из
`layout.html` + `partials.html` + своей страницы.

## Бот

Основной поддерживаемый интерфейс — `BOT_STYLE=legacy` в `.env`.
Он использует rich-сообщения со штатными кнопками и обычный Telegram HTML
при отказе rich API. Старые персональные настройки не перекрывают `.env`;
`/start` открывает кабинет без закреплённого выбора интерфейса.
HTML-виджеты оставлены экспериментальными: `BOT_STYLE=html` требует
доступного widget API на выбранном сервере Telegram. Карточка использует навигацию «Доступ /
Устройства / Помощь / Ещё». На главной — срок, статус и показатели подписки;
обновление вынесено в компактную кнопку. Переходы обновляют `chat_data` того же сообщения.
Платёжные действия используют прежние серверные проверки.
Отказ widget API не означает успешное открытие карточки. Опросы и
платёжные счета Telegram сохраняют свой нативный формат.

Используется telego `v1.13.0` с Bot API 10.4. `/status` открывает тот же
раздел подписки в выбранном режиме. Отдельного третьего интерфейса нет.
Устройства разбиты на страницы по три записи; дополнительные места
показываются отдельно с периодом расчёта. Отвязка требует подтверждения.
Подключение начинается с выбора платформы, затем показывает установку
приложения и добавление подписки. Возврат из управления устройством
сохраняет страницу списка. Ссылки открываются синхронно при нажатии,
их значения передаются только в личном `chat_data`. Копирование передаётся
штатной кнопке в отдельном обычном сообщении: Telegram Web блокирует
копирование из защищённого виджета, не возвращая ошибку вызову `copyText`.
Регрессионные проверки интерфейса: `node --test internal/bot/widgets/interface.test.cjs`.

`/diagnostics` проверяет подписку, наличие ссылки и свободные места.
Отдельный веб-пульт `/admin` включает заказы и повтор выдачи оплаченного
заказа, очередь обращений, каталог 40 демонстрационных экранов
(`/admin/screens`) и редактор темы с живым предпросмотром
(`/admin/appearance`). Сохранение оформления и повтор выдачи доступны
владельцу; в Telegram `/admin` есть быстрый переход к оплаченным заказам.
Настройка темы и изолированного предпросмотра: [docs/bot-interface.md](docs/bot-interface.md).

Виджет доступен только в личном чате с ботом. Персональные сведения
хранятся в `chat_data`, публичное состояние не используется. Если сервер
не поддерживает `sendWidget`, владелец переключает `.env` на `BOT_STYLE=legacy`
и перезапускает процесс. Пользовательский `/view` не меняет эту настройку.
Актуальная карточка: `internal/bot/widgets/interface.html`. Состояние и
действия сохраняются в PostgreSQL; запросы проверяют личный чат, владельца,
сообщение, текущую версию и видимость кнопки. Повторные запросы одной версии
после перехода не выполняются. Не запускайте локальный бинарник и Docker
с одним токеном одновременно: Telegram допускает один `getUpdates`.

Команды: `/start`, `/menu`, `/view`, `/status`, `/buy`, `/subscription`, `/devices`, `/promo`,
`/referral`, `/support`, `/info`, `/weblogin`, `/help`, `/paysupport`,
`/cancel`. Для сотрудников: `/admin`, `/stats`, `/tickets`, `/grant`,
`/reply`, `/close`; с правом `broadcast.send` — `/announce` (рассылки);
для владельца — ещё `/polls` (опросы) и `/partners`
(партнёрская программа).

Оплата: карточные шлюзы присылают вебхук, звёзды — `successful_payment`.
Заказ, который не удалось выдать сразу, добивается фоновой задачей;
напоминания о сроке и о неоплаченном счёте включаются в `/settings` и
переменными `REMIND_*`.

Награда за приглашённых выбирается: днями подписки или деньгами на
внутренний баланс. Переключается и в боте (экран «Друзья»), и в кабинете
на сайте. По умолчанию берётся `REFERRAL_MODE`.

## Отличия от Python-версии

Из Python перенесены рассылки с выбором аудитории, предпросмотром и
подтверждением, компенсация 3 дня из обращения и подписанный вебхук Remnawave
для первого подключения и уведомлений о новых устройствах. Очереди рассылок
и событий сохраняются в PostgreSQL. Подробности и ограничения:
[операции legacy](docs/legacy-operations.md).

Не перенесены «идеи» (предложения пользователей), динамическая загрузка
Python-расширений и уведомления о порогах трафика. Напоминания о сроке
строятся по базе. Мультипродление пакетов
устройств вместе с тарифом сведено к одному заказу на вид покупки.

Партнёрская программа, помощник на базе LLM, опросы, живая переписка в
поддержке и отдельная админка на сайте вернуты в Go-версии — но в том виде,
в каком это удобнее живому сервису, а не как было в Python.

Журнал шагов выдачи сохранён: `order_fulfillment_steps` и
`storage.Journal`. Каждый шаг выполняется один раз, а панели
передаётся абсолютный срок, посчитанный на первом проходе. Повторный вебхук
или фоновая попытка не выдают второй период, не активируют промокод
второй раз и не начисляют реферальную награду дважды.

Сохранено: схема и идентификаторы заказов, ссылки на оплату, триалы,
реферальные начисления, промокоды, тикеты, лимит устройств и его
понижение после истечения докупленных слотов.

## Разработка

```bash
make fmt vet test     # форматирование, статический анализ, тесты
go test ./...
sqlc generate         # необязательно: типизированный слой по sqlc.yaml
```

Тесты с настоящей базой запускаются отдельно: им нужна Postgres, и трогать
рабочую нельзя.

```bash
# База в Docker — быстрее всего
docker run -d --name vivid-pg -e POSTGRES_PASSWORD=postgres -p 5433:5432 postgres:15-alpine
docker exec vivid-pg createdb -U postgres vivid_test

TEST_DATABASE_URL="postgres://postgres:postgres@localhost:5433/vivid_test?sslmode=disable" go test ./...
# или
make test-db TEST_DB="postgres://postgres:postgres@localhost:5433/vivid_test?sslmode=disable"
```

Проверить, что приложение поднимается на существующих данных, можно
дампом: `pg_restore` в подготовленную базу, затем

```bash
go run ./cmd/dbcheck  -url "postgres://postgres:postgres@localhost:5433/vivid?sslmode=disable"
go run ./cmd/websmoke -url "postgres://postgres:postgres@localhost:5433/vivid?sslmode=disable"
```

Каждый пакет тестов работает в своей схеме (`payments_test`, `storage_test`,
`web_test`), поэтому пакеты идут параллельно и не мешают друг другу.
Схема пакета пересоздаётся один раз за прогон: остатки прошлого прогона
не могут повлиять на результат. Без `TEST_DATABASE_URL` тесты с базой
пропускаются, а не падают.

Что закрыто тестами: перенос субъектов, выдача заказа (продление ровно
один раз, награды за реферала и партнёра), промокоды, триалы, покупка с
баланса, слоты устройств, партнёрская программа, тикеты, проверка подписи
`wata` и разбор уведомлений шлюзов, клиент модели, помощник поддержки,
права доступа к админке и CSRF, живая переписка и страницы сайта.

[Состояния заказов, управление автопродлением, очередь проблем и поддержка](docs/customer-flow.md).
Автоматические проверки для GitHub описаны в `.github/workflows/test.yml`.

Отдельно закрыты чистые правила, где ошибка стоит денег: разбор и печать
сумм, скидки и промокоды, награды партнёров, выбор «лучшего» тарифа,
настройки окружения, форматирование текстов бота и разметка сообщений.
Тесты с базой проверяют и то, что человек не должен получить дважды:
оплату подписки, промокод, пробный период, награду за приглашение и
уведомление об истечении.
