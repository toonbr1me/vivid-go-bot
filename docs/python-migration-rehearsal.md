16 ноября 2026 года. Проверяемый код: `2621b19`.

**Вывод: цепочка покупки работает на копии Python-базы, но переключать production пока рано.** Подтверждены несовместимость исторических статусов и два пропуска проверки данных в Platega webhook. Оформление Berloga в проверке не использовалось.

## Что действительно проверено

- Источник данных — согласованный `pg_dump` рабочей Python-БД на `alex-nether`, PostgreSQL 15. Получение дампа выполнялось с `default_transaction_read_only=on`.
- Дамп восстановлен на `yotta-ger` в отдельном PostgreSQL 17. Контрольные SHA256 источника и получателя совпали. Production-БД и существующий development-стенд не изменялись.
- На копии выполнены настоящие `storage.Open`, SQL-миграции и `MigrateSubjects` из Go-проекта.
- HTTP-запросы действительно шли с `alex-nether` на `yotta-ger`. Тестовый процесс использовал настоящие `web.Server.Handler`, CSRF, checkout, Platega adapter, webhook inbox и выдачу из `payments.Service`.
- Клиент был синтетическим. Платёжный HTTP API и интерфейс панели были эмуляторами; реальные деньги и рабочие профили не использовались. Фоновые задания и Telegram-бот не запускались.
- Временный вход принимал только IP `alex-nether` и запросы с HMAC. Дополнительная проверка запрещала обработку заказов реальных клиентов. После прогона правило firewall удалено, тестовый процесс и отдельная БД остановлены; недоступность порта проверена с исходного сервера.

Это проверка интеграции Go с реальной структурой и историей данных, а не проверка настоящего банковского платежа или полного production-запуска `cmd/vivid`.

## Обязательные правки перед переключением

### 1. Совместимость исторических статусов — P1

В Python выдача не переводит обычный оплаченный заказ в `provisioned`; она заполняет `provisioned_at`. В Go многие выборки ориентируются на строку `status`.

| Статус в исходном дампе | Заказов | С заполненным `provisioned_at` |
| --- | ---: | ---: |
| `paid` | 646 | 646 |
| `manual_granted` | 418 | 418 |
| `trial_granted` | 1024 | 1024 |
| `declined` | 375 | 0 |
| `pending` | 13 | 0 |

Последствия подтверждены данными и условиями в коде:

- `storage.Operations` считает 646 уже выданных заказов ожидающими доступа; `AttentionOrders` также выбирает их в проблемную очередь.
- `domain.Order.Progress` показывает для `paid` выдачу или её задержку, не учитывая заполненный `provisioned_at`. `manual_granted`, `trial_granted`, `declined` попадают в неопределённый статус.
- `SubscriptionForOwner`, напоминания, аудитория активных подписчиков и сводка подписок ожидают `status='provisioned'`. В исходной истории таких строк нет. Сама панель может вернуть активную подписку, но эти выборки истории и fallback БД работают неверно.
- В дампе 268 строк с будущим `expire_at`: 243 обычных, 10 ручных, 15 пробных. Это число строк заказов, а не уникальных клиентов или подтверждение активности в панели.

**Что исправить:** добавить идемпотентную миграцию совместимости и единые признаки «оплата подтверждена» / «выдача завершена». Сохранить исходный статус для аудита. Выданные `paid/manual_granted/trial_granted` привести к единой модели выдачи; `declined` сопоставить с `failed`. Очередь доступа должна обязательно учитывать `provisioned_at IS NULL`.

На копии в транзакции проверено преобразование 2088 выданных заказов и 375 отказов; затем выполнен `ROLLBACK`. Это только проверка количества и выборок, готовая миграция в код не добавлена.

Нельзя ограничиться массовой заменой статусов: после неё пробные и подарочные выдачи попадут в текущий `Stats.PaidOrders`, считающий все `provisioned`. Нужно отдельно определить показатели покупок и выдач, проверить `HasPaidProvisioning`, сегменты и trial eligibility. Суммы и даты исторических операций изменять не нужно.

**Повторной выдачи старых 646 оплат в текущем снимке не обнаружено:** у всех заполнен `provisioned_at`, а `PendingProvisioning` выбирает только строки без него. Несовместимость статусов сама по себе не доказывает двойное начисление срока.

### 2. Проверка Platega callback — P1

`PlategaProvider.Verify` допускает подтверждение без суммы и валюты. `Service.HandleEvent` сравнивает сумму только при ненулевом указателе, валюту — только при непустой строке. Также отсутствует сопоставление `event.TransactionID` с `order.PaymentLinkID` для обычного checkout.

**Что исправить:** для обычного подтверждённого Platega-платежа требовать валидные сумму, валюту и ID, сверять связь транзакции с заказом; при недостаточных или противоречивых данных запрашивать состояние через API и выдавать доступ только по проверенному результату. Для рекуррентных списаний нужен отдельный контракт, поскольку ID подписки и транзакции различаются. Уже существующий `Platega.CheckPayment` проверяет ID, payload, сумму и валюту — callback должен обеспечивать сопоставимую проверку.

Обязательные регрессионные сценарии: отсутствующие и некорректные поля, чужая транзакция, другой заказ, повтор, параллельные события, отказ → успешная оплата, частичный сбой выдачи. Оба воспроизведённых дефекта требуют **верных merchant/secret**; это не подтверждение возможности обхода аутентификации посторонним.

### 3. Старые неоплаченные счета — P2

В снимке 13 `pending`: у всех есть платёжная ссылка и ID, у всех отсутствует `payment_expires_at`. Go `LivePendingOrders` считает такие ссылки живыми без ограничения по возрасту. Это может возвращать клиенту старый счёт. Автосверка при этом выбирает только заказы моложе трёх дней.

**Что исправить:** перед переключением сверить эти счета с провайдерами, получить подтверждённые сроки или конечные статусы. Для legacy-ссылок без срока определить ограничение повторного использования. Сохранить возможность обработать позднюю реальную оплату. Политику и маршруты поздних callback проверить отдельно; в этом прогоне старые счета с настоящими шлюзами не сверялись.

### 4. Диагностика миграции — P2

`cmd/dbcheck` печатает ошибки отдельных SQL-проверок, но продолжает работу и может вернуть exit code 0. Также он выводит количества без автоматической проверки ожидаемых инвариантов.

**Что исправить:** ненулевой код при ошибке или нарушении инварианта, машиночитаемый отчёт, проверка статусов и денежных контрольных сумм. Успешный запуск миграций должен быть отдельным результатом от готовности данных к переключению.

## Условия следующего прогона и переключения

1. Внести перечисленные исправления в основной код и повторить миграцию на свежем снимке; проверить сохранение исходных денежных полей и связей.
2. Повторить негативные HTTP-сценарии: оба найденных дефекта должны перестать приводить к выдаче.
3. Проверить YooKassa, рекуррентные платежи, допустройства, промокоды и балансы на той же схеме. В этом межсерверном прогоне проверялась обычная подписка через Platega; наличие 790 исторических YooKassa-заказов не означает проверки этого адаптера.
4. Проверить настоящую панель отдельным тестовым профилем, контракт эквайринга в sandbox, запуск фонового восстановления и legacy Telegram. Подтвердить соответствие старых профилей и аккаунтов без development namespace; `devgo` не подходит для доступа к production-профилям.
5. Подготовить переключение HTTPS/callback, Telegram и единственного набора workers. Не запускать Python и Go одновременно как владельцев одной production-базы и одних внешних операций. Учитывать уже открытые счета и уведомления в пути.
6. Снять финальный backup после остановки записи Python. Откат после новых Go-покупок требует сохранения и сверки новых операций: простой возврат старого дампа потеряет оплаты. Проверить процедуру отката до переключения.

Проверка закончилась без переключения сервиса. Python app/DB на `alex-nether` и Go development app/DB/subpage на `yotta-ger` остались `healthy`; `/healthz` development отвечает 200. Закрытые копии дампа и остановленная rehearsal-БД оставлены на серверах в приватном каталоге для продолжения проверки.
