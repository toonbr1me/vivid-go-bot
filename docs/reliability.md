# Обработка покупок и восстановление после сбоев

## Баланс и доступ

Покупка с баланса использует `storage.CreateBalanceOrder`: условное списание
полной суммы и создание оплаченного заказа происходят в одной транзакции.
Недостаточный баланс или ошибка записи откатывают оба изменения.
Старый `DeductBalance` сохранён как совместимый помощник с ограничением
списания остатком; для покупки его использовать нельзя.

`Journal.Once` блокирует шаг advisory-блокировкой Postgres до чтения и
начислений. Изменения внутри БД и результат шага фиксируются вместе.
Изменения подписки одного субъекта дополнительно сериализуются между
процессами через отдельное соединение с advisory-блокировкой. Блокировка
не занимает соединение рабочего пула. Нужны прямое подключение к Postgres
или session pooling; transaction pooling для этой блокировки не подходит.

Абсолютный срок фиксируется в журнале и учитывает уже зарезервированные
периоды других оплаченных заказов. Повтор не уменьшает более поздний срок
в панели. Изменения доступа сторонними программами напрямую в панели
не участвуют в блокировках приложения.

Триал резервируется вместе с устойчивым заказом. Ошибка выдачи не удаляет
заявку: повтор пользователя и фоновые задачи продолжают тот же заказ.
Бонусные дни хранятся в шаге журнала и не теряются при ошибке панели.
Подарки и ручные выдачи также сохраняют заказ до изменения панели.

Промокоды резервируются при создании заказа под блокировкой строки кода.
Общий и персональный лимиты учитывают незавершённые покупки. Неоплаченные
резервы освобождаются по сроку ссылки; оплаченные сохраняются до выдачи.
Резерв превращается в активацию в транзакции шага журнала. Поздняя настоящая
оплата принимается и после истечения ссылки; оплаченное обещание выполняется,
даже если за это время другой клиент занял освободившийся резерв.

## Шлюзы

Заказ сохраняется до запроса на создание платёжной ссылки. Полученные ID
и URL записываются отдельно. Ошибка API не означает, что платёж не создан;
такой заказ не объявляется оплаченным или окончательно отменённым.

Проверенные карточные вебхуки и события Telegram Stars сохраняются в
`payment_inbox`. Успешный HTTP-ответ означает сохранение проверенного
события. Неизвестный заказ или сбой выдачи оставляют событие для повтора.
Ошибка временного запроса к API при проверке вебхука возвращает 503,
неверная подпись — 400, ошибка сохранения — 500.

Зависшие карточные платежи за последние три дня сверяются с API раз в
минуту, по 25 заказов за проход. Один заказ проверяется не чаще раза в
минуту, включая кнопку «Я оплатил». Ошибка одного провайдера не прерывает
сверку остальных заказов. Проверяются также неуспешные/отменённые заказы:
подтверждённая оплата приоритетнее прежнего отказа. Возвраты этим процессом
не оформляются.

Протоколы сверки:

- ЮKassa — существующая проверка `GET /payments/{id}` по ID платежа.
- Platega — [GET /transaction/{id}](https://docs.platega.io/проверка-статуса-оплаты-платежа-29203844e0).
- WATA — [поиск успешных транзакций по orderId](https://api.wata.pro/transactions).
  Закрытая ссылка сама по себе не считается подтверждением оплаты.

Если шлюз создал платёж, но ответ с его ID потерялся, ЮKassa/Platega
восстанавливаются через вебхук; без ID их фоновая сверка невозможна.
WATA дополнительно ищется по номеру заказа. Stars восстанавливаются из
полученного платёжного события; опрос API для Stars не добавлялся.

Реальные платёжные вызовы в проверках не выполняются: интеграционные тесты
используют отдельный Postgres и поддельную панель/шлюзы.

## Уведомления и поддержка

Напоминания об окончании берут максимальный сохранённый срок подписки
клиента. Продление новым заказом исключает старое окончание из выборки.
Известно просроченные ссылки не попадают в напоминания о неоплате;
для старых ссылок без срока сообщение предлагает продолжить оформление
в боте, не обещая действующую ссылку.

Доставка использует claim с пятиминутной арендой. `sent` записывается после
успешного ответа Telegram; при ошибке возможен повтор. Сбой между фактической
доставкой и записью `sent` может привести к повторному уведомлению.

Помощник проверяет весь контекст перед запросом к модели, исключает
внутренние сообщения и не продолжает переписку сотрудника. Фильтруются
распознаваемые секреты, email, похожие на карточные номера и телефоны.
Это эвристика, а не универсальный детектор любых персональных данных.
Правила передаются системным сообщением. Просьба модели передать вопрос
сотруднику меняет режим обращения и сохраняет уведомление в переписке.

## Проверки

`go test ./...` без `TEST_DATABASE_URL` пропускает проверки с базой.
Для полного прогона задайте отдельную тестовую PostgreSQL. Параллельные
агенты должны использовать разные базы: тесты очищают таблицы своих схем.
Новые проверки реализации лежат в `codex_*_test.go`; тестовые файлы
второго агента не изменялись.
