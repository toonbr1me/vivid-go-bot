# Переключение Python → Go

Дата: 16 ноября 2026 года. Production: `berlogapn.com`, целевой сервер `yotta-ger`.

## Исправления совместимости

- Миграция `0008_python_orders.sql` сохраняет `legacy_status`, переводит уже выданные Python-заказы в `provisioned`, а `declined` — в `failed`. Суммы, даты оплаты и срок доступа сохраняются.
- Операционная очередь требует отсутствия `provisioned_at`. Бесплатные выдачи не увеличивают число платных заказов и выручку.
- Подтверждённый callback Platega требует сумму, валюту, ID транзакции; обычный платёж должен соответствовать ID созданного счёта. Рекуррентные списания сохраняют отдельное связывание.
- Старые платёжные ссылки без срока не используются повторно и не отправляются в напоминаниях. Позднее подтверждение оплаты по существующему заказу по-прежнему может обрабатываться.
- `dbcheck -json` сообщает нарушения инвариантов и возвращает ненулевой код при ошибке проверки.

Проверки перед выкладкой: полный Go integration suite на выделенном PostgreSQL, `go vet`, 21 JavaScript-тест. Добавлены регрессии миграции Python-статусов, сохранения исходного статуса, учёта бесплатных выдач, очереди доступа и неполных/чужих Platega-платежей.

## Размещение

Отдельный Compose-проект `vivid-go-production`, каталог `/opt/vivid-go-production-20261116`. Конфигурация: `deploy/production/compose.yml`. PostgreSQL 17, отдельный том. Приложение публикуется только на `127.0.0.1:38080`; публичный HTTPS обслуживает nginx. Development-проект и его база остаются отдельными.

Production получает настройки и ключи действующего Python-сервиса, без их вывода в журнал и Git. `REMNAWAVE_NAMESPACE` пуст: Go ищет существующие production-профили. Пользовательский каталог, счета, балансы, история поддержки и настройки переносятся дампом. Оформление — встроенное Vivid, Telegram — legacy. Тема Berloga не монтируется.

## Порядок переключения

1. Собрать и проверить бинарники; подготовить отдельную БД и образ без запуска production-бота.
2. Восстановить свежий предварительный снимок, сохранить контрольные суммы исходных таблиц, выполнить миграцию и сравнить данные. Read-only preflight проверяет разрешение существующих профилей панели.
3. Повторить межсерверный тест на отдельной rehearsal-БД; реальные production-платежи не эмулировать в рабочей базе.
4. Остановить Python app на `alex-nether`. Снять финальный дамп после остановки записи, проверить SHA256 при переносе.
5. Восстановить финальный дамп в целевую БД, повторить миграцию, сверку и preflight. Запустить единственный production Go app.
6. Переключить маршрут `berlogapn.com` на `yotta-ger`; на старом ingress сохранить проксирование на новый сервер для клиентов со старым DNS. `nora.berlogapn.com` и рабочая страница подписки сохраняют прежний маршрут.
7. Проверить публичный HTTPS, авторизацию, приём webhook, Telegram polling, фоновые задания, состояние БД и отсутствие запущенного Python app.

## Откат

До запуска Go можно вернуть Python app и исходные proxy-конфигурации: исходная production-БД на `alex-nether` остаётся на месте. Backup и прежние конфигурации сохраняются в приватных каталогах серверов.

После приёма новых запросов Go нельзя просто восстановить старый дамп и потерять новые записи. Сначала остановить запись и сохранить целевую БД, затем перенести и сверить новые заказы, платежи и выдачи. Нормализованные статусы должны учитываться при возврате Python; исходные исторические значения сохранены в `legacy_status`.

Фактический результат переключения и контрольные количества дописываются после проверки работающего production.
