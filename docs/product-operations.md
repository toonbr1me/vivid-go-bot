# Поддержка, продажи и эксплуатация

Изменения подготовлены в исходниках. Эта инструкция не означает, что новая
версия и резервное копирование уже включены на production.

## Доступ и настройки

Роль `support` работает с обращениями. Финансовые, партнёрские и управляющие
страницы проверяют отдельные права независимо от видимости пунктов меню.
`app_settings` проходит разрешённый список `config.EditableSettings`.
Токены, `ADMIN_IDS`, настройки подключения и авторизации берутся из окружения;
ранее сохранённые в БД значения этих ключей больше не подменяют окружение.

`/admin/settings` проверяет значения до записи и публикует целый снимок
настроек. Экраны, платежи и задачи читают его без перезапуска. При нескольких
экземплярах остальные нужно перезапустить для чтения изменений из БД.
`/admin/staff` выдаёт `support`/`admin` или отзывает доступ. Владельцы из
`ADMIN_IDS` через эту форму не изменяются.

## Поддержка

`/admin/tickets`: свободные, свои, ожидающие ответа, открытые и закрытые,
счётчики, последнее сообщение, страницы. SSE обновляет очередь с сохранением
фильтра. Отзыв роли прекращает доступ к обновлению очереди и переписки.

Доступны захват, ответ, передача активному сотруднику, отсрочка на 24 часа,
закрытие, повторное открытие и внутренние заметки. Чужой действующий захват
запрещает ответ и изменение. Ответ свободному обращению назначает исполнителя.
Изменение и аудит сохраняются транзакционно. Заметки не попадают в историю,
SSE и уведомления клиента. В Telegram доступны те же действия и фильтры.

## Каталог, заказы и финансовые операции

`/admin/plans`: тарифы и пакеты устройств, срок, целая цена в рублях,
устройства, сортировка и доступность. ID неизменяем; тариф снимается с
продажи без удаления истории. Новые ID: до 24 строчных латинских букв,
цифры, `_`, `-`. Для тарифа задаются собственные трафик и сквады.
Пустой трафик наследует общую настройку, `0` — безлимит, `100GB` — лимит.
Пустые сквады наследуют настройки сервиса. Устройства `0` наследуют базовый
лимит; положительное число задаёт лимит тарифа. Сохраняются уже оплаченные
слоты и ручные увеличения в панели.

Новый заказ сохраняет срок, цену, устройства и снимок профиля. Изменение
каталога не меняет купленные условия. Снимок сохраняют подарки и рекуррентные
заказы. Исторические заказы без снимка используют прежний совместимый путь.

`/admin/orders` ищет по всей истории: заказ, транзакция, ID платёжной ссылки,
имя, Telegram ID, аккаунт, провайдер, статус и период. Последний день периода
включается. Поиск не подтверждает оплату. Повтор выдачи остаётся доступным
только для оплаченного заказа. `/admin/customers/{id}` связывает доступ,
баланс, заказы и обращения. Старые Telegram-заказы разрешаются в аккаунт
при поиске без изменения исторических строк. `/history` и история Telegram
показывают все покупки с пагинацией.

`/admin/withdrawals`: одобрение и списание баланса атомарны и не повторяются
при повторе запроса. Сам перевод выполняется отдельно.
`/admin/refunds`: журнал рассмотрения и сверки возвратов. Для завершения нужен
номер фактического возврата провайдера; заказ становится `refunded`.
Повторный callback не возвращает его в выдачу. Эта форма не инициирует
банковский перевод и не отзывает уже выданный доступ. Активированный подарок
требует отдельного решения по выданному доступу.

## Подарки

`/gifts` на сайте и в Telegram: доступные для дарения тарифы, оплата балансом
или включёнными шлюзами, история и одноразовые ссылки. Промокоды и
автопродление для подарка не применяются. Покупка создаёт заказ `gift` и
запись подарка до обращения к шлюзу; покупателю доступ не выдаётся.

Готовый подарок имеет код `gift_…`, ссылку сайта и Telegram deep link.
Срок хранения оплаченного подарка не ограничен. Первому получателю
транзакционно создаётся один оплаченный заказ выдачи. Свой подарок
активировать нельзя. Повтор тем же получателем возвращает тот же заказ,
другому получателю отказывает. Панель недоступна — заказ выдаётся фоном
после восстановления. Активному клиенту подарок продлевает подписку.

Подарок сохраняет купленные условия после изменения каталога. Повтор той
же формы покупки балансом не списывает деньги второй раз. Новый выбор
покупки получает новый идентификатор. История переживает перезапуск.

## Удержание и поведенческие рассылки

К последним суткам добавлены предупреждение за 1–3 дня, возврат через 3–30
дней после окончания и напоминания о дополнительных устройствах. Для
раннего предупреждения и возврата проверяется продление в панели.
Включённое автопродление не сопровождается предложением оплатить вручную.
Напоминания о брошенных счетах ограничены одним успешным сообщением за 30 дней.

`REMIND_NOT_CONNECTED_HOURS`: одно напоминание о доступе, выданном за
последние семь дней, без первого подключения. Отсутствующее в панели поле
`firstConnectedAt` означает неизвестность: бот молчит. При нескольких
профилях отсутствие подключения должно быть известно у всех. Учитываются
настройки уведомлений и журнал доставки. Проверка фактов для сегментов
работает и с выключенной отправкой, начиная с шести часов после выдачи.

В `/announce` добавлены аудитории:

- `trial_only`: получили триал, но не имеют оплаченной покупки;
- `abandoned`: незавершённая оплата старше часа за последние 30 дней без
  последующей успешной покупки;
- `expired`: последний срок истёк 3–30 дней назад;
- `not_connected`: активный доступ и подтверждённое отсутствие первого
  подключения по проверке панели за последние сутки.

Отключение уведомлений об активности исключает из поведенческих аудиторий.
Состав фиксируется в черновике, до отправки видны число получателей и
предпросмотр. Выбор аудитории сам по себе рассылку не запускает.

### Автоматические кампании

`/admin/campaigns` сохраняет правила для этих четырёх сегментов. Создание
не запускает отправку: сначала открывается предпросмотр с текстом, числом
подходящих клиентов, лимитом, датой начала и часами в часовом поясе сервиса.
Отдельная кнопка включает именно просмотренную версию. Устаревшая форма
не может включить изменённый текст.

Каждую минуту кампания подбирает новых подходящих клиентов и ставит сообщения
в существующую устойчивую очередь. Несколько экземпляров приложения не
создают повторных партий. Лимит за 24 часа проверяется также непосредственно
перед доставкой: вчерашняя отложенная очередь не обходит сегодняшний лимит.
Один человек получает не больше одного сообщения автоматических кампаний
за 24 часа, даже если одновременно подходит нескольким кампаниям.
Ошибки и неоднозначные попытки также занимают это окно.

Период повторения `0` исключает повторную постановку человека в эту кампанию;
при необходимости повторов можно задать от 7 до 365 дней. Учёт начинается
с постановки в очередь, включая впоследствии пропущенные сообщения.
Изменение текста и условий ставит кампанию на паузу и отменяет ещё не
начатые отправки. Повторное включение требует нового предпросмотра.
Уже переданное Telegram сообщение может дойти после нажатия паузы.

Перед доставкой снова проверяются сегмент, разрешение уведомлений,
активность кампании, права автора и промокод. Оплативший клиент исключается
из предложения завершить покупку; оплаченные заказы, ожидающие выдачи,
и включённое автопродление исключают из сегмента истёкших подписок.
Вне выбранных часов сообщения ждут следующего окна. Отозванные права
автора или недоступный промокод автоматически ставят кампанию на паузу;
причина видна в админке.

История показывает партии, доставленные, ожидающие, пропущенные,
ошибочные и неоднозначные сообщения. Поддержка не имеет доступа к
созданию и включению кампаний. Все изменения сохраняются в журнале действий.

## Мониторинг и резервное копирование

`/healthz` проверяет HTTP-процесс, `/readyz` — PostgreSQL.
`/admin/operations` показывает очереди, возраст оплаченного заказа и проходы
задач. `/metrics` отдаёт Prometheus только при заданном `METRICS_TOKEN` и
заголовке `Authorization: Bearer …`; без токена endpoint закрыт.
Метрики: `vivid_paid_waiting`, `vivid_paid_oldest_seconds`,
`vivid_payment_inbox_pending`, `vivid_broadcast_pending`,
`vivid_job_failures`, `vivid_job_last_success_timestamp_seconds`.

После трёх ошибок задачи подряд владельцы получают уведомление не чаще раза
в час. Отдельная задача проверяет выдачи старше 10 минут, платёжные события
старше 15 минут и просроченные проходы. Панель не включена в readiness,
чтобы её временный отказ не отключал сайт и приём оплат.

Подготовлен отдельный overlay с custom dump каждые шесть часов, проверкой
чтения архива, SHA256, атомарным переименованием и хранением 14 дней:

```sh
docker compose -f deploy/production/compose.yml -f deploy/production/backup.compose.yml up -d backup
```

При отдельном размещении production сохраните относительные пути скриптов
из overlay либо исправьте mount. `db.env` содержит действующие
`POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PASSWORD`. Копии находятся в
`deploy/production/backups`; каталог также следует включить во внешнее
резервирование сервера. Healthcheck проверяет возраст последней копии.

Проверка восстановления использует отдельный PostgreSQL без открытого порта
и с временным хранилищем. Скрипт допускает только БД `vivid_restore_test`,
проверяет checksum, восстанавливает архив с остановкой при ошибке и читает
основные таблицы:

```sh
docker compose -f deploy/production/compose.yml -f deploy/production/backup.compose.yml --profile restore-check run --rm restore-check
docker compose -f deploy/production/compose.yml -f deploy/production/backup.compose.yml --profile restore-check stop restore-db
```

Для остановки только проверки не используйте `down`: базовый compose
содержит production-приложение и его БД.

## Проверки

Тесты используют отдельный `TEST_DATABASE_URL`, локально PostgreSQL 15.19;
CI остаётся на PostgreSQL 17. Новые проверки охватывают права, приватность
заметок, захват и передачу, старые платежи, выплаты, возвраты, сегменты,
настройки без перезапуска, оплату и конкурентную активацию подарков.
Настоящие списания и сообщения клиентам не выполняются.

Проверка в Docker на Linux с PostgreSQL 17 прошла: весь Go-набор с `-race`,
`go vet`, 21 JavaScript-тест и HTTP-проверки собранного приложения.
Перезапуск сохранил заказы, подарки, балансы и внутренние заметки.
Backup создал архив с корректным SHA256; restore восстановил его на отдельном
PostgreSQL, сверка данных и `dbcheck` завершились без нарушений.

Повторяемый стенд не читает рабочий `.env`, использует синтетические ключи
и внутреннюю Docker-сеть без внешних платежей или Telegram:

```sh
docker compose -p vivid-verify -f deploy/verification/compose.yml --profile test build app tests
docker compose -p vivid-verify -f deploy/verification/compose.yml up -d --wait db app
docker compose -p vivid-verify -f deploy/verification/compose.yml --profile test run --rm tests
docker compose -p vivid-verify -f deploy/verification/compose.yml --profile test run --rm smoke
docker compose -p vivid-verify -f deploy/verification/compose.yml -f deploy/production/backup.compose.yml up -d --wait backup
docker compose -p vivid-verify -f deploy/verification/compose.yml -f deploy/production/backup.compose.yml --profile restore-check run --rm restore-check
docker compose -p vivid-verify -f deploy/verification/compose.yml -f deploy/production/backup.compose.yml --profile restore-check down
```

Последняя команда удаляет только контейнеры и сеть проекта `vivid-verify`;
том тестовой БД и созданные архивы сохраняются.
